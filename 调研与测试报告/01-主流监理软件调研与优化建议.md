# 主流监理软件调研与本项目优化建议

> 报告日期：2026-09-20
> 调研对象：广联达、品茗、Procore、筑业云、易监理、监理通、河狸云、简道云工程等主流产品
> 结合对象：本项目「监理现场管理系统」（Spring Boot 3.2 后端 + 26 个静态 HTML 页面）

---

## 一、市面主流产品调研结论

### 1.1 代表产品速览

| 产品 | 定位 | 突出特点 | 对本项目的借鉴价值 |
|---|---|---|---|
| **广联达 BIM+智慧工地** | 施工/监管全链条平台 | IoT 实时采集、自动分析建模、数据驱动决策大屏 | 数据可视化与自动统计方向 |
| **品茗智慧工地监管平台** | 政府/企业级监管 | 对人员、质量、安全、设备、环境"全过程、全要素"监管 | 监管要素覆盖度的对标清单 |
| **Procore（国际）** | 施工协作平台 | 移动端检查清单（Inspection Checklist）、**无网络也能现场作业**、照片标注、观察/整改项与后台自动同步 | 现场移动作业与离线能力的标杆 |
| **筑业云** | 监理资料管理 | 进度/质量/安全/成本四控，**监理表格资料模板丰富、可出图归档** | 资料规范化方向 |
| **易监理 / 监理通 / e监理** | 监理行业垂直 | 移动端现场拍照上传、实时上报，多方（业主/监理/施工）协同 | 移动取证 + 多方协同 |
| **河狸云监理方案** | 监理数字化 | **工序报验→待办通知→到场验收→整改单→闭环** 的工作流；"尽职免责、有据可查" | 业务闭环设计的直接对标 |
| **简道云（低代码）** | 通用搭建平台 | 表单/流程按需定制、灵活扩展 | 表单字段可配置化思路 |

### 1.2 行业共性：主流产品的"六大件"

调研发现，无论国内国外，成熟的监理/智慧工地产品都具备以下六类能力：

1. **移动端优先的现场作业**：旁站、巡视、平行检查（监理规范 7 大手段：审查、见证、旁站、停工待检、巡视、平行检验、验收）都在手机/平板上完成，拍照 + 定位 + 时间戳自动水印，支持弱网/离线暂存。
2. **问题闭环工作流**：发现问题 → 自动生成整改单/监理通知单 → 推送责任人 → 施工方整改回复 → 监理复核销项 → 归档留痕。状态机清晰（待整改/整改中/待复核/已闭环/已升级）。
3. **资料与台账自动生成**：监理日志、月报、会议纪要由日常巡检数据**自动汇总生成**，而非重新手工录入；支持国标/地方表格式的打印导出。
4. **数据大屏与驾驶舱**：项目概况、人员到岗、安全隐患分布、整改及时率等图表化呈现，给总监理工程师/甲方一个"看板式"管理视角。
5. **消息驱动协同**：待办、催办、超期预警通过站内信 + 微信/短信推送；审批、复核不依赖打开电脑。
6. **知识库与标准驱动**：检验批/分项工程库、工作标准库驱动现场检查项，减少人为遗漏。

## 二、本项目现状与差距分析

### 2.1 已具备的能力（值得肯定）

- 22 个业务模块 Web 端基本齐全：日记、日志、月报、安全日志、通知单、巡检、会议纪要、台账、人员/部门/权限等，**功能覆盖面达到行业产品的"管理后台"主流水平**。
- 统一登录 + JWT + 角色校验（`@RequireRole`）权限体系完整，本次复测确认 401/403 区分正确。
- 已有审核闭环雏形：日记/日志/安全日志支持 approve 流程；`sub-item-database`、`work-standard-config` 已具备"标准库驱动"的种子能力。
- 数据契约统一（ApiResponse + PageResult）、分页钳制、XSS 统一防护，工程质量较好。

### 2.2 与行业标杆的主要差距

| 维度 | 行业主流做法 | 本项目现状 | 差距等级 |
|---|---|---|---|
| 移动化 | App/小程序现场拍照、定位打卡、离线暂存 | 仅 Web 页面（有小程序指南文档未实施）；supervision-diary 有照片字段但无移动端采集入口 | ★★★ 大 |
| 业务闭环 | 问题→整改单→回复→复核→销项全程状态机 | 通知单/联系单有回复与审核，但**无统一"隐患-整改-复查"状态机**，各单据状态字段各自为政 | ★★★ 大 |
| 资料自动化 | 日志/月报由巡检数据自动汇总 | 月报、报表页与日记/巡检数据**未打通**，仍需人工填写 | ★★☆ 中 |
| 数据大屏 | 项目驾驶舱、地图、视频联动 | index.html 有统计卡片，无图表钻取、无趋势图 | ★★☆ 中 |
| 消息推送 | 站内信 + 微信/短信 | 仅站内消息中心，无外部推送 | ★★☆ 中 |
| 文件取证 | 照片水印（时间/地点/人员）、附件预览 | 有文件上传（白名单校验良好），无水印、无图片预览体验 | ★☆☆ 小 |
| 尽职免责留痕 | 操作留痕 + 电子签名 | 有操作日志，无电子签名/手写签认 | ★☆☆ 小 |

## 三、具体优化建议（按优先级排序）

### P0：先修复本次测试发现的业务缺陷（详见测试报告）

1. **部门删除增加关联校验**：`DepartmentService.delete` 目前软删除且不检查是否仍有人员/子部门挂靠，会产生孤儿 `deptId` 脏数据，且与前端提示文案（"含有子部门或人员的部门不可删除"）矛盾。建议：删除前校验 `users`、子部门引用，被引用时返回业务错误。
2. **项目台账"查看"弹窗改造**：当前详情弹窗内容为写死的静态假数据（恒显示"城东综合体项目"），必须改为按 id 调 `GET /projects/{id}` 渲染；同时删除列表 HTML 中硬编码的 6 行示例数据，避免后端故障时误导用户。
3. **项目表单补字段校验**：建设单位、总监理工程师标了 `*` 却不校验；"建设单位"根本没有提交给后端（DTO 缺字段），列表永远显示"—"。

### P1：体验与一致性（低成本、高感知）

4. **去掉原生 alert/confirm**：项目保存校验、人员重置密码等处使用阻塞式原生弹窗，与系统整体的自定义弹窗/Toast 风格不一致，统一改为 Toast + 自定义确认框。
5. **人员"离职/停用"交互优化**：停用后记录从默认列表"凭空消失"（后端默认过滤 inactive），建议列表增加状态筛选 Tab（在岗/离职/全部），删除做成"移入离职+可恢复"。
6. **部门管理页补搜索框**：与人员管理页对齐（本次测试确认该页无搜索能力）。
7. **窄屏适配**：人员管理页存在约 1038px 硬最小宽度，1024×768（老笔记本/投影仪投屏）出现横向溢出；表格容器 `overflow-x:hidden` 会直接裁切内容，应改为 `auto` 并允许工具栏换行。

### P2：对标行业的能力建设（中期规划）

8. **微信小程序落地**（已有 WECHAT_MINIPROGRAM_GUIDE.md 基础）：优先做三件事——现场拍照上报（巡检/旁站）、监理日记语音转文字快填、待办消息推送。这是行业差距最大的一块，也是监理人员真实工作场景（大量时间在工地现场而非办公室）。
9. **统一"隐患-整改-复查"状态机**：把通知单、联系单、巡检问题的状态收敛为一套枚举（草稿→已发送→待整改→整改回复→待复核→已闭环/已升级），任何单据闭环后自动归档并在日记/月报中生成条目。
10. **报表自动生成链路**：`diary-report`、`supervision-monthly-report`、各统计页改为从日记/巡检/通知单原始数据自动汇总（按项目+时间范围聚合），人工只做补充修改，减少重复录入。
11. **仪表盘图表化**：引入轻量图表库（如 ECharts），展示近 30 天日志提交趋势、隐患分类占比、整改及时率；卡片支持点击钻取到对应模块列表。
12. **照片证据增强**：上传照片自动加"时间+项目+上传人"水印（后端 Thumbnailator 或前端 canvas 均可），附件支持点击预览大图。

### P3：工程化底座（长期收益）

13. **前端组件化收敛**：26 个页面内联 CSS 重复度高，建议抽出公共 `app.css`（设计令牌/按钮/表格/弹窗），或按知识库建议另建独立前端工程；避免"改一处样式要改 26 个文件"。
14. **接口自动化回归**：本次产出的 API 测试脚本（测试工作区/api-functional-tests.ps1）可扩展为全模块回归集，纳入发版前必跑清单。
15. **软删除策略统一**：部门软删、人员软删、项目硬删，三种策略并存易埋坑，建议统一约定并在文档中说明。

## 四、不建议照搬的行业功能（避免过度建设）

| 行业功能 | 不建议现阶段做的理由 |
|---|---|
| IoT 设备接入（塔吊/环境/闸机） | 依赖硬件与施工方配合，超出监理单位控制范围，投入产出比低 |
| BIM 模型联动 | 监理场景使用频率低，多数项目无竣工模型交付要求 |
| 视频大屏监控 | 需要工地摄像头资源，且涉及与业主责任边界问题 |
| 计量计价 | 属于造价咨询业务，与本项目"现场监理"定位不同 |

> 小结：本项目 Web 管理后台的骨架已达到行业中上水平，最优先的差异化投入方向是「移动端取证 + 隐患整改闭环 + 报表自动生成」三件事，它们共同指向监理行业的核心诉求——**尽职免责、有据可查、少填表**。
